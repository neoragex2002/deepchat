# **实施现状与下一步（Status）**

**受众：** PM / QA / 技术负责人

**指导原则：** 本文档旨在提供 DeepChat Agent 项目当前实施状态的全面概述，突出已交付的架构亮点和核心能力，明确识别当前存在的遗留问题和技术债务，并清晰规划未来的战略方向。它与 `overview/summary.md` 形成呼应，并为关键决策和未来规划提供依据。

### **1. 核心架构与功能交付（Step 0–4）：从原型到稳健框架的架构演进**

DeepChat Agent 团队已成功完成了 Step 0 到 Step 4 的核心开发任务，将 Agent 的核心工作流从一个初期原型重构为一个稳定、可观测且高度可控的健壮框架。这一阶段的成果显著提升了系统的可靠性、可维护性和用户体验。

#### **1.1 基础架构与流程稳定性**

通过引入一系列基础性架构原则，系统从根本上解决了旧有流程中存在的竞态条件、UI 状态不一致以及职责边界模糊等核心痛点。

* **单一真理来源 (SSoT) 与 Revision 护栏机制**
    * **成果：** UI 内容的权威更新**唯一**来源于后端发出的 `MESSAGE_EDITED` 事件。每次权威更新都携带一个递增的 `revision` 标识，确保前端仅采纳最新、最权威的状态。
    * **价值：** 彻底根除了因 `STREAM` 事件和数据库更新事件时序错乱而导致的 UI 闪烁、状态回滚等用户体验问题。这为前端提供了**高度可预测**、**易于调试**且**始终一致**的消息渲染基础。

* **阶段性同步 (Phased Synchronization) 与同步屏障**
    * **成果：** 在 `stop=tool_use` 这一关键业务节点，系统引入了 `STREAM.DRAIN/ACK` 同步屏障机制。该机制确保所有流式提示（`STREAM`）在前端完全处理完毕后，后端才进入“纯 ME 阶段”（由 `MESSAGE_EDITED` 驱动的权威操作）。
    * **价值：** 从机制上杜绝了“后到的 `STREAM` 帧覆盖已提交的权威状态”这一核心乱序问题，为后续的授权、执行、限流等复杂业务逻辑提供了**严格的时序保障和状态一致性**。

* **Provider “仅收集” (Collect-Only) 模式**
    * **成果：** `LLMProviderPresenter` 的职责被明确且大幅简化，它**不再**执行工具、判断授权或处理限流。其核心功能**仅限于**从 LLM 流中解析并收集 `planned_tool_calls`，并在 `STREAM.END` 事件中提交给 `ThreadPresenter`。
    * **价值：** 实现了模块职责的清晰分离和解耦。所有业务决策和流程控制权被统一上收到 `ThreadPresenter` 层，使得核心流程更加**内聚、可控且易于维护**。

#### **1.2 Agent 核心能力**

基于稳定、可预测的新架构，Agent 团队已成功构建了强大且可靠的核心能力，显著增强了 Agent 的智能和自主性。

* **统一的工具调用流程 (“纯 ME 阶段”)**
    * **成果：** 在同步屏障之后，所有工具的限流决策、用户授权交互、工具实际执行以及结果写回，都由 `ThreadPresenter` **统一调度**。所有状态变更均通过 `MESSAGE_EDITED` 事件进行原子化、权威性的更新。
    * **价值：** 流程变得高度**可预测和可调试**。无论是授权、执行还是限流，都遵循统一的“决策 → 提交 → 通知”模式，避免了状态机复杂性。

* **原子化的 `id-only` 配对**
    * **成果：** 工具调用、权限块、执行结果等所有关联对象的匹配，**严格**基于全局唯一的 `tool_call_id`。所有无 `id` 的临时提示块都不会被持久化或参与核心逻辑。针对非原生 FC 和缺失 ID 的原生 FC 片段，Provider 层会自动合成稳定的 `tool_call_id` (例如 `tc-${eventId}-...`)。
    * **价值：** 彻底解决了在并行或同名工具调用场景下，因依赖名称或顺序而导致的“授权错配”问题，确保了**结果与权限的精确绑定**。

* **可靠的 R2 继续作答**
    * **成果：** 在工具执行完毕后，系统能够可靠地将“工具调用+执行结果”的完整配对以结构化形式注入到新的 LLM 上下文中（`R2` 阶段），从而驱动模型基于准确的工具执行结果继续生成自然语言回复。
    * **价值：** 保证了 Agent 多步推理的**连贯性和正确性**，显著提升了多轮对话中 Agent 的响应质量。

#### **1.3 高级流程与鲁棒性**

系统为 Agent 增加了处理复杂场景和异常情况的能力，使其在实际应用中表现出更高的鲁棒性。

* **全流程取消机制 (ACE：Abort → Commit → End)**
    * **成果：** 实现了统一的 `Abort → Commit → End` 取消模型，覆盖了从 **R-prepare（搜索）**、**S（流式）**、**屏障等待** 到 **X（执行）** 的所有 Agent 流程阶段。
    * **价值：** 用户可以在任意时刻安全、可靠地中止 Agent 的任务，系统状态会**优雅地收敛**到“已取消”的最终态，并释放相关系统资源。这极大地提升了用户对 Agent 的控制感。

* **R-prepare 搜索（迷你阶段）**
    * **成果：** 在 Agent 首次思考（`R` 阶段）之前，系统引入了一个独立且高效的搜索子流程。该流程通过多次 `MESSAGE_EDITED` 事件驱动，在前端展示搜索进度。搜索触发策略已收敛，仅在首轮 R 和 `msg_retry` 时触发。
    * **价值：** 显著提升了 Agent 获取**实时信息和外部知识**的能力，从而增强了回答的**准确性和权威性**，有效减少了 LLM 的幻觉问题。该流程与主工具调用流程解耦，互不干扰。

#### **1.4 可观测性**

* **结构化日志体系**
    * **成果：** 建立了全新的、结构化的日志体系，包括用于追踪关键业务决策和流程流转的**审计日志** (`logs/audit/*.jsonl`)，以及用于深度调试和回溯 LLM/工具交互细节的 **IO 日志** (`logs/io/*.json` 和 `logs/io-detail/*.jsonl`）。
    * **价值：** 关键的业务流程节点（如 `BARRIER`, `PERM`, `EXEC`, `LIMIT`, `SEARCH`, `CANCEL`, `PROVIDER`, `UI` 等）都有了**结构化、低噪且易于分析**的日志记录。这极大地提升了系统的**可观测性**、**故障排查效率**和**审计能力**。

### **2. 已修正功能点（Fixes & Optimizations）**

以下列出了在 Step 0-4 阶段，团队为提升系统稳定性、一致性和效率所做的关键修复和优化：

* **`MESSAGE_EDITED` 事件发射源统一**
    * **修正：** `MessageManager` 不再自发 `MESSAGE_EDITED` 事件（其 `editMessageSilently` 方法仅返回 revision）。`ThreadPresenter` 统一在关键业务边界（如 `handleLLMAgentEnd`, `handlePermissionResponse` 等）调用 `editMessageSilently()` 后发射权威事件。
    * **价值：** 确保了 `ThreadPresenter` 作为事件协调者的唯一性，进一步强化了 SSoT 原则。

* **Renderer 消息合并逻辑简化**
    * **修正：** `mergeAssistantMessage()` 中的键生成仅对 `tool/permission` 使用 `tool_call.id`；无 ID 的块被视为不可跨事件/版本合并的临时项。
    * **价值：** 提升了 UI 合并的精确性，避免了因名称或时间戳兜底导致的错配。

* **严格 `id-only` 的 UI 提示**
    * **修正：** `handleStreamResponse()` 的 `tool_call: 'start'|'running'` 分支在无 ID 时不再创建新的提示块（no-op）。
    * **价值：** 杜绝了无 ID 提示导致的错配与重复，确保 UI 提示的准确性。

* **移除流内结果回注与冗余字段**
    * **修正：** 移除了 `tool_call end/error` 流事件的执行结果回注，仅保留提示态（`handleStreamResponse` 中 `end/error` 分支仅保留提示，不设最终态）。删除了 `tool_call_response_raw` 的产出、类型与引用，主流程已不再消费该字段。
    * **价值：** 避免了“双真源”问题，简化了数据流，降低了噪音，使结果统一由权威 `MESSAGE_EDITED` 下发。

* **FC `tool_call_id` 规范化**
    * **修正：** Provider 层为**非原生 FC** 统一使用 `tc-${eventId}-${index}-${ts}` 合成 ID；为**原生 FC** 在缺失 ID 且有 `index` 时合成 `tc-${eventId}-native-${index}-${ts}` 并建立映射。未闭合标签追加 `-incomplete` 后缀以便审计。
    * **价值：** 确保了 `id-only` 策略在所有工具调用场景下的可行性，大大提升了配对的稳定性。

* **移除“授权即复述” (Auth-then-Replay) 流程**
    * **修正：** 彻底移除了旧有的“授权后复述一轮”的低效流程。`ThreadPresenter` 在收到用户授权后，会**直接执行** (`executeGrantedToolsAndContinue`) 内存中已规划的 `tool_call`，而**非**发起新一轮 LLM 请求来“诱导”模型重发调用。
    * **价值：** 显著降低了 API 调用成本和端到端延迟，使授权流程更高效、更可靠。

* **移除伪 `tool` 消息注入**
    * **修正：** `ThreadPresenter` 在构建 R2 上下文时，不再注入“Permission granted...”之类的伪 `tool` 消息。
    * **价值：** 减少了不必要的 Token 消耗，并使 R2 上下文更干净、更符合原生 FC 协议（仅包含真实的 `assistant.tool_calls` 和 `role='tool'` 结果）。

* **移除执行期 `permission_required` 回退**
    * **修正：** L2 物理层（`ToolManager.callTool`）若判定权限不足，直接返回 `errorCode: 'permission_denied'` 的执行错误；`ThreadPresenter` 不再有处理 `requiresPermission` 回退的逻辑。
    * **价值：** 简化了权限处理逻辑，避免了不必要的往返和状态转换，使权限决策更直接、更高效。

* **权限块状态防回退**
    * **修正：** `finalizeLastBlock()` 不再修改权限块 或 `loading` 的工具块，仅将普通内容类块标记为 `success`。权限块合法状态明确为 `pending | granted | denied | error`，不使用 `success`。
    * **价值：** 根除了“权限块在流过程中被错误标记为 success”导致的 UI 降级噪声，确保状态单调。

* **搜索功能优化**
    * **修正：** R-prepare 搜索触发策略收敛（仅首轮 R 与 `msg_retry`；R2 禁止）；搜索重写上下文支持“用户边界” 并剔除助手侧内容；增强了搜索流程的可观测性（新增 `Search/Gate` 等日志）。
    * **价值：** 避免了不必要的搜索触发，提高了搜索的精确性和效率，并增强了调试能力。

* **Barrier ACK 偶发超时修复**
    * **修正：** Renderer 在 `handleStreamDrain` 中正确回显 `sseqLast`，主进程 `ackStreamDrain` 即时解除屏障，消除短暂超时与卡顿。
    * **价值：** 提升了屏障机制的响应速度和用户体验。

* **审计日志换行双重转义修复**
    * **修正：** `writeAudit` (JSONL) 使用真实 `\n`，提升可读性与后处理兼容性。
    * **价值：** 优化了日志输出质量，方便日志分析。

* **待授权 `END(final=true)` 一致性优化**
    * **修正：** 进入“等待授权”即结束本阶段流式（`final: true`），前端解除“生成中”。
    * **价值：** 提升了 UI 状态的准确性，避免用户误以为仍在生成中。

* **`simulatePageScrolling` 窗口存活检测与降级**
    * **修正：** 增加了 `isWindowAlive` 检查 和多处短路，异常情况下降级为 warn，不影响主流程；修复了搜索窗口滚动竞态导致的 `Object has been destroyed` 错误。
    * **价值：** 提升了搜索模块在窗口生命周期管理上的鲁棒性。

* **STREAM.START 兜底清理 DRAIN 围栏/序列缓存**
    * **修正：** 在 `handleStreamStart` 中增加了兜底清理 DRAIN 围栏/序列缓存的逻辑。
    * **价值：** 防御异常序列导致继续阶段帧被围栏丢弃的边界情况，提升系统稳定性。

* **搜索块去重与并发防抖**
    * **修正：** 使用 `searchingMessages` 集合 和复用既有搜索块 的逻辑。
    * **价值：** 避免了重复打开搜索窗口与重复 UI 插块，优化了用户体验。

### **3. 当前遗留问题与技术债务**

尽管核心框架已趋稳定，但仍存在一些待处理事项。这些是团队未来持续优化和战略投资的重点领域。

* **3.1 一次性授权可靠性与资源管理问题**
    * **现状澄清：**
        * ✅ 已实现“授权后直执”：`ThreadPresenter` 在授权后直接执行已规划的 `tool_call`，不再“复述一轮”。
        * ✅ 并发键粒度为 `server|tool`：`ToolManager` 使用 `serverName|originalName` 和 `serverName|finalName` 双键写入 和消费，确保“一次性授权只能用一次”。
    * **仍待优化 (技术债务)：** `ToolManager` 内的 `oneTimeGrantsByServerTool` 尚无 TTL（自动过期）与容量上限治理；长期运行可能出现授权项残留。
    * **优先级：** 高
    * **后续计划：** 为一次性授权 Map 增加 TTL（建议 30 分钟）与容量上限（建议 1000），采用“惰性清理 + 周期清理”的组合；继续保持 `server|tool` 精细粒度，不引入粗粒度兜底键；保留现有“直执”路径。

* **3.2 LLM 上下文与 Token 效率优化**
    * **问题描述：**
        * **非原生 FC 提示词冗余：** 对不支持原生 FC 的模型，函数调用提示词冗长且每轮重复注入到用户消息前缀，显著浪费 Token。
        * **非原生 FC 工具结果冗长：** 工具执行成功后，注入完整的 `<function_call>{...response}</function_call>` 文本记录，可能导致上下文体积过大；额外 user 文本引导也消耗 Token。
        * **图片事件写入文本占位：** 收到 `image_data` 事件后，向 `currentContent` 追加 `"[Image data received: ${mime}]"` 占位文本，增加上下文 Token 且无助于模型推理。
        * **空内容 Assistant 消息：** 即使 `currentContent` 为空，但若存在 `tool_calls`，仍会 push 一个 Assistant 消息，造成轻微 Token/结构开销。
        * **工具定义/Schema 每轮注入：** 即使不需要工具或工具定义体积大，每轮仍会注入完整的工具定义。
        * **原生 FC 工具结果过大：** `toolResponse.content`（即 `subMsg.tool_call.response`）直接作为 `tool` 消息注入，可能导致下一轮整合的 Token 成本显著上升。
    * **优先级：** 中
    * **后续计划：** 优化非原生 FC 提示词为 system 消息一次性注入；对工具结果进行摘要化处理；移除图片事件文本占位；优化空 Assistant 消息的注入逻辑；实现工具定义按需、轻量注入；对原生 FC 工具结果过大时进行摘要化。

* **3.3 配置硬编码与维护成本**
    * **问题描述：**
        * **日志开关默认值对齐：** `LOG_IO_DETAIL` 在 `docs_luy/background/logging-spec.md` 中声明默认值为 `false`，但源码中可能存在不一致（*注：经核查 `src/main/logger/config.ts` 默认值为 false，此项已对齐*）。
        * **限流策略配置化：** `ThreadPresenter` 的工具数上限与模式为常量（`TOOL_CALL_LIMIT_MAX = 100`, `TOOL_CALL_LIMIT_MODE = 'soft_degrade'`）。
        * **搜索选择器维护成本：** 多引擎选择器在 `searchManager.ts` 中硬编码，变更成本高、可测试性弱。
    * **影响：** 限制了系统的**运行时可配置性**和**业务策略的灵活性**，不利于 A/B 测试、多租户配置或快速响应业务需求变化。
    * **优先级：** 中
    * **后续计划：** 将限流策略（软/硬模式及其阈值）、搜索的默认参数、部分权限的自动审批规则等关键业务和技术配置，从代码常量迁移到可外部配置的参数中。参数化/模板化搜索提取逻辑。

* **3.4 文档与代码注释的清理与对齐**
    * **问题描述：** 在项目迭代过程中，部分旧文档和代码注释可能仍引用了已废弃的日志路径（如 `logs/runtime-events`）、旧的流程逻辑（如“复述”）或过时的术语。
    * **风险：** 增加了新成员的**认知负担和学习曲线**，可能导致开发者对系统行为产生误解，降低**开发效率和代码维护性**。
    * **优先级：** 低
    * **后续计划：** 进行一次全面的文档和代码注释审查与对齐工作，确保所有参考资料都反映系统当前的最优实践和最新状态。

* **3.5 参数校验与动作分类器覆盖度**
    * **问题描述：** `ToolManager` 对工具入参不做校验，而 `shell/shell_info` 等内置工具在服务端运行时进行 Zod 校验。`ToolManager.determinePermissionType` 启发式（H）虽然可覆盖多数写动词，但仍需更系统的测试集合来防回归（尤其是 Windows PS/CMD 特有模式）。
    * **影响：** 潜在的参数校验缺失或不一致，以及启发式分类的覆盖度不足，可能导致工具执行失败或意外行为。
    * **优先级：** 低
    * **后续计划：** 审计所有内置工具的运行时参数校验。引入命令 → 权限类型映射的回归样例库，确保“确定性分类器”的稳定性。

* **3.6 单条回复内 `tool_call` 顺序保真问题**
    * **问题描述：** 当 LLM 在同一条回复内计划输出“文本A + <tool_call> + 文本B”时，若 `tool_call` 被权限中断（进入屏障和 ME 阶段），文本B 往往延后到工具执行/结果之后的 R2 阶段再出现，改变了原文本的时序。
    * **影响：** 可能影响用户对信息连贯性的感知，尤其在对时序敏感的场景。
    * **优先级：** 低
    * **后续计划：** 评估是否需要供应商/协议级适配以实现“未看到 `tool_result` 仍可继续输出同条回复文本”的能力（S2 模式），或接受当前行为作为权衡。

### **4. 下一步计划 (Next Steps)**

下一阶段的工作将聚焦于 Agent 系统的战略性增强，特别是安全性和核心性能的持续优化。

#### **4.1 主要阶段：Step 5 - Agent 安全架构落地**

这是 DeepChat Agent 下一阶段的核心任务，旨在为 Agent 提供一个坚不可摧的“物理”和“语义”双重安全保障，为 Agent 的广泛应用奠定信任基础。

* **目标：** 实现 `workflows/agent-security.md` 中定义的 L1 语义权限系统和 L2 内核级物理守护系统。
* **关键任务：**
    1.  **执行器层安全强化：杜绝命令注入与环境隔离**
        * **杜绝 Shell 注入：** 强制所有外部命令通过 `argv` 数组（例如 `subprocess.run(..., shell=False)` 模式）执行，**严禁**使用 `shell=True` 或任何允许元字符注入的机制。
        * **建立内核级沙盒：** 构建一个**强隔离**的执行环境，利用 `rbash`（命令白名单）、`AppArmor`（提供更深层次的系统级访问控制）和 `ulimits`（实施资源限制）来防止资源耗尽攻击。
    2.  **语义层安全强化：防止 LLM 欺骗与意图误判**
        * **实现 L1 确定性动作分类器：** 在 `ThreadPresenter` 或 `ToolManager` 中增加一个**强制校验层**。该分类器不信任 LLM 自报的 `action` 字段，而是根据命令的**第一个词（即二进制名称）**进行确定性分类。
        * **固化最小动作空间：** 在 L1 策略中明确 Agent 的最小动作空间 (`Inspect`/`Read`/`Write`/`Network`)，并为每个动作定义默认处理策略（如 `AUTOGRANT`, `CONFIRM`, `AUTODENY`）。
    3.  **L1 与 L2 的桥接：** 落地“启动时交底 + 可靠的 JIT-Refresh (基于退出码)”机制，解决能力发现和上下文遗忘问题。

#### **4.2 近期优化与清理**

在启动 Step 5 的同时，团队将并行处理以下短期优化任务，以持续完善当前交付并提升开发效率。

* **文档体系补完与标准化：**
    * **任务：** 按照既定的文档结构，完成所有 `overview/`, `workflows/`, `progress/`, `verification/` 目录下文档的撰写和整合。
    * **关键：** 为 `workflows/` 目录下的关键流程文档**补全 Mermaid 时序图**和**具体日志示例**，确保文档的清晰度和可操作性。

* **验证用例与测试覆盖率强化：**
    * **任务：** 将 `verification/test-plan.md` 中的“观察点/验收标准/排查路径”部分补充完整，使其成为一份可以独立执行的 QA 指南。
    * **关键：** 对核心流程和关键安全特性进行**额外的端到端测试覆盖**，确保系统的鲁棒性。

* **配置化与开关机制落地：**
    * **任务：** 将限流策略（软/硬模式及其阈值）、搜索的默认参数、部分权限的自动审批规则等关键业务和技术配置，从代码常量迁移到可外部配置的参数中。
    * **关键：** 增加可观测性开关，允许在运行时动态控制日志输出级别和类型。
